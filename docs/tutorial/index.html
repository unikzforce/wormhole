Chapter 00 · Foundations

00One Ethernet segment, anywhere on Earth

Goal: learn the machine Data plane: XDP + TC Encapsulation: VXLAN (MAC-in-UDP) Repo: this is your code, generalized

Everything Wormhole does reduces to one promise: machines in different places behave as if they were plugged into the same Ethernet switch. Same subnet, working ARP, working broadcast — even if one machine is in Berlin and the other in a cloud region. This tab teaches the four mechanisms that make the promise real. Every later scenario is just this machinery pointed at a different market.

Vocabulary you need (only four terms)

VTEP

VXLAN Tunnel End Point. The box at the border of a site that wraps outgoing Ethernet frames into UDP packets and unwraps incoming ones. In Wormhole, a VTEP is any Linux machine running the agent.

VNI

Virtual Network Identifier — a 24-bit number inside the VXLAN header. Frames with different VNIs never mix. It is the isolation boundary: one VNI = one virtual Ethernet segment.

Underlay / Overlay

The underlay is the real IP network (office fiber, the internet, a cloud VPC). The overlay is the virtual Ethernet segment floating on top of it. Hosts see only the overlay.

Flood-and-learn

How a switch discovers topology: note the source MAC of every frame you see (learn), and send frames for unknown destinations everywhere (flood) until someone answers.

The big picture — watch the packet travel

The packet walk, step by step (badges ①–⑤ in FIG 0.1)

  1. src emits a normal frame on eth1. Its OS thinks 192.168.1.11 is a neighbor on the LAN, so it ARPs, gets a reply (more on how in a second), and sends a plain Ethernet frame to aa:c1:ab:44:10:01. Nothing special runs on src.
  2. border1's XDP program catches the frame on eth1 — inside the NIC driver, before the kernel even allocates a socket buffer. It learns the source (aa:c1:ab:11:10:01 lives on eth1), looks up the destination MAC in the mac_table BPF map, and finds: "reachable via border 3.3.3.2". It encrypts the frame with bpf_crypto_encrypt, prepends outer Ethernet + IP + UDP + VXLAN headers with bpf_xdp_adjust_head(-50), and redirects to eth2. One program, one core, no context switch.
  3. The underlay sees boring UDP. Whatever sits between the two eth2 ports sees only 3.3.3.1:<random> → 3.3.3.2:4790. The inner frame — addresses, payload, everything — is AES-GCM ciphertext. In the lab this hop is one veth cable; in production it is the internet.
  4. border2's XDP program unwraps it on eth2. It validates the auth tag, decrypts, learns "aa:c1:ab:11:10:01 lives behind border 3.3.3.1" (MAC and which remote VTEP — two facts in one lookup), strips the 50 outer bytes, and redirects the original frame out eth1.
  5. dst receives an ordinary Ethernet frame on eth1, indistinguishable from one that crossed a desk-side switch. It replies; the same machinery runs in reverse, and now both VTEPs have fully learned both MACs — every subsequent packet takes the fast path.
💡 Concept — why the first packet is special

Before any learning has happened, border1 has no idea where dst's MAC is. And the very first thing src sends is an ARP broadcast ("who has 192.168.1.11?"). Broadcasts must reach every node in the segment — including remote sites. XDP cannot copy a packet to multiple destinations, so the XDP program does XDP_PASS, handing the frame up one layer to a TC program which can clone (bpf_clone_redirect): once to each local internal port, and once per remote VTEP (each clone encapsulated). dst's ARP reply comes back unicast, both VTEPs learn from it, and flooding stops. Flooding is the expensive bootstrap; learning is the steady state.

Anatomy of the encapsulation

📊 Order of magnitude — the MTU tax

With a standard 1500-byte underlay MTU: 1500 − 20 (outer IP) − 8 (UDP) − 8 (VXLAN) − 8 (nonce counter) − 16 (auth tag) ≈ 1440 bytes for the inner frame → inner IP MTU ≈ 1426 → clamp TCP MSS to ~1380 to be safe. In data centers you instead raise the underlay MTU to 1600+ ("baby giant frames") and keep a clean 1500 inside. On the WAN you clamp. Your repo already uses xdp.frags, so jumbo frames on the overlay work too.

⚠️ Reality check — two port trivia items

IANA's VXLAN port is 4789; the Linux kernel driver historically defaulted to 8472; this codebase uses 4790 (which IANA assigned to VXLAN-GPE). Between your own VTEPs any port works — but firewalls with protocol inspection may only recognize 4789. Second: the outer UDP source port is randomized per flow (your get_ephemeral_port()) — that's not laziness, it's how underlay routers spread tunnel traffic across parallel paths (ECMP hashes the 5-tuple, and everything else about the tunnel is constant).

💼 Business lens — the one upgrade that turns this into a product

Flood-and-learn is beautiful and needs zero coordination — but it leaks traffic and scales poorly past a handful of sites. Every serious commercial fabric (EVPN, cloud SDNs) replaces discovery with a control plane that already knows the answer: when an agent learns a MAC, it reports it; the Controller pushes it to every other agent's mac_table proactively. Flooding then only covers true broadcasts. Same data plane you have today — the Controller is the product. Keep this in mind through every scenario tab: data plane = open source credibility, control plane = revenue.

Chapter 02 · Flagship scenario

02Hybrid multi-cloud: one network, three providers

Buyer: platform engineering Encryption: required — public internet Kernel: ≥ 6.10 (bpf_crypto) Motion: self-serve, Tailscale-style

The customer: Meridian, a mid-size fintech. Production VMs in AWS eu-central-1, a data-science stack in GCP, and a rack of bare metal in a Frankfurt colo (market-data feed handlers that must live near the exchange). Three underlays, three IP plans, three firewall regimes — and the engineering team just wants one network.

Today's pain: AWS↔GCP↔colo connectivity means site-to-site VPNs or transit gateways: L3-only, per-GB processing fees, and every migration means re-IP'ing. Their legacy pricing engine discovers peers via UDP broadcast — it simply cannot work across an L3 VPN. And the DR plan ("bring standbys up in the colo with the same IPs") is a fantasy on routed networks, because an IP address can only live inside one routing domain at a time — unless the network is stretched at L2.

How Wormhole fits

Agent — host mode (clouds)

Cloud fabrics forbid L2 on the wire (no ARP, no promiscuous mode — the VPC only delivers packets to known IP/MAC pairs). So inside AWS/GCP the overlay terminates inside each VM: the agent creates a tap device, attaches XDP to it, and tunnels from the VM itself.

Agent — gateway mode (colo)

Where you own the switches, one agent (or an HA pair) is the VTEP for the whole site — exactly your current vxlan_agent border design. Zero changes to the servers behind it.

Controller

Node enrollment (SSO/OIDC for humans, tokens for machines), topology + MAC distribution, key epochs (tab 07), and the admin console. This is the SaaS you bill for.

Crypto module

bpf_crypto AES-GCM on every frame that leaves a site. Policy-driven: intra-VPC traffic can skip crypto (the cloud already isolates it), inter-site traffic never does.

Packet walk — db-replica (GCP) reads from the colo pricing-engine

  1. The GCP VM writes to 172.16.3.30. Kernel ARPs on the tap device; the agent answers locally from Controller-pushed state (ARP suppression — no flood ever leaves the VM for known hosts).
  2. XDP on the tap encrypts the frame, wraps it, and sends UDP from the VM's own NIC to the colo gateway's public IP. To Google's fabric this is ordinary egress UDP.
  3. The colo gateway VTEP validates + decrypts in XDP on eth0 and redirects the plain frame out eth1 onto the rack switch. The pricing-engine — a bare-metal box with no agent installed, its eth0 numbered straight on the overlay — answers normally.
  4. Return path mirrors. Steady-state adds ~60 bytes and two XDP passes per packet; no proxies, no per-flow state on any middlebox.
📊 Order of magnitude — what the incumbent path costs

AWS Transit Gateway: ~$0.02/GB processed plus per-attachment hourly fees; inter-region/site VPN throughput caps per tunnel (~1.25 Gbps) force ECMP gymnastics. At Meridian's 80 TB/month cross-site, TGW processing alone is ≈ $1,600/mo before egress — and it still can't carry a broadcast frame or move an IP. Wormhole's pitch: flat per-node pricing, cloud egress is the only per-GB cost left, and the two "impossible" workloads (broadcast discovery, same-IP DR) just work.

⚠️ Reality check — the two things that bite in the field

MSS/PMTUD: encapsulation shrinks the effective MTU (~1426 inner); broken ICMP paths turn that into mysterious hangs. The agent must clamp TCP MSS on the tap by default — make the safe thing the default thing. NAT traversal: v1 honestly requires one reachable UDP endpoint per site (public IP or port-forward). UDP hole-punching with the Controller as rendezvous — the trick Tailscale perfected — is the fast-follow feature.

💼 Business lens — first 90 days if you pick this scenario

(1) Host-mode agent with tap + XDP + crypto and a hosted Controller with magic-link enrollment — "two VMs in different clouds, same subnet, in under 5 minutes". (2) A published benchmark: Wormhole vs ZeroTier vs Tailscale, same hardware, iperf + pps + CPU% — your XDP numbers are the launch story. (3) Free tier ≤ 5 nodes, usage-based above. The wedge users: game-server operators, GPU-cloud arbitrageurs, HFT-adjacent shops — people who feel the userspace ceiling today.

Why not just run OVS like everyone else?

Open vSwitch is the default answer and its costs are structural: a kernel-module datapath with a userspace daemon (ovs-vswitchd) that handles every flow-table miss — under churn, misses stampede the daemon ("upcall storms") while the fast path still pays full sk_buff + conntrack overhead. The practical result on real clouds is whole CPU cores per hypervisor burned on packet plumbing. An XDP pipeline is a flat run-to-completion program: no upcalls, no flow-cache cliff, no conntrack unless you ask for it.

📊 Order of magnitude — the margin argument that closes this sale

Say virtual switching consumes 4–6 cores of every 64-core hypervisor under load (a common OVS reality) and XDP does the same job in ~1. On 1,000 hypervisors that's 3,000–5,000 cores returned to inventory — sellable vCPUs, not infrastructure tax. At even $20/core-month retail, the data plane pays for its own license many times over. You are not selling technology; you are selling reclaimed rack capacity.

💡 Concept — the security work the edge must do

Multi-tenancy is only as strong as edge enforcement. The per-VM tap position lets the XDP program pin each VM to its assigned MAC + IP (drop spoofed sources — port security in software), enforce security-group rules as map lookups, and rate-limit per tenant. And because keys are per-VNI (tab 07), offering "encrypted VPC" as a premium SKU is a policy flag, not a project.

⚠️ Reality check

This buyer needs carrier-grade: HA controller (the fabric must keep forwarding if the control plane dies — agents cache last-known state), live migration of MACs, BGP/EVPN interop at the fabric border for their existing routers, and 18–24 months of hardening. The prize is symmetric: 10–20 customers is a real company, and none of them can churn off a data plane their whole cloud runs on.

Chapter 05 · Same primitives, telecom prices

05Private 5G: the UPF is a tunnel switch — you already build those

Buyer: private-5G integrator / MVNO Encryption: not needed — PDCP covers the air Data plane reuse: same skeleton, new headers GTM: be the fast data plane for open 5G cores

The customer: a container port deploying private 5G — hundreds of AGVs, 8K crane cameras, thousands of sensors. In every 5G network, one box touches all user traffic: the UPF (User Plane Function). It terminates GTP-U tunnels from the radio, applies per-session rules, and forwards to the internet or local apps. It is the throughput bottleneck and the license line-item of the whole deployment.

The insight that makes this tab exist: GTP-U — the tunneling protocol of all mobile networks — is structurally VXLAN's sibling. Outer IP, outer UDP, an 8-byte tunnel header carrying an ID, inner packet. A UPF is a tunnel-encap/decap switch with per-tunnel policy. You have already written 90% of that machine.

That's a contained integration with an existing community who already measures UPF benchmarks for sport.

Chapter 06 · The agent's second job

06East-west security: the network that watches itself

Buyer: CISO / SecOps New code: flow maps + export — data plane unchanged Motion: upsell to every existing deployment Market: NDR / network observability

Security teams see traffic entering and leaving the datacenter (north-south) through firewalls and proxies. What they famously cannot see is workload-to-workload traffic inside (east-west) — which is exactly where an intruder moves after the first foothold. Traditional answers: SPAN ports and hardware taps (miss everything that never crosses a physical switch), or per-app agents (deployment friction, userspace losses).

Wormhole's agent already holds a privileged seat: an XDP program on every interface of every enrolled host touches every packet anyway — to forward it. Counting it costs a map update. This tab is not a new product; it's the second act of the same deployed fleet.

The telemetry pipeline (and why it's nearly free)

  1. In XDP: after the forwarding decision, update a per-CPU flow map keyed {vni, src, dst, proto, ports} → {packets, bytes, tcp_flags, first_seen, last_seen}. A hash update on a hot cache line: tens of nanoseconds.
  2. New flow only: first packet of an unseen key pushes one event through a ring buffer — the same new_discovered_entries_rb pattern your switch agent already uses for MAC discovery. Per-packet events would melt userspace; per-flow events are a trickle.
  3. Agent: drains the ring buffer, aggregates, ships IPFIX/OTLP to the collector every few seconds.
  4. Collector: maintains the org-wide communications graph and scores changes: first-seen edges, fan-out spikes, SYN-heavy scanning, beaconing periodicity, byte-count exfil anomalies.
💡 Concept — "first-seen edge" beats signatures

Classic IDS asks "does this payload match a known attack?" — an arms race you lose on encrypted traffic anyway. Graph-based NDR asks a colder question: "has this conversation ever happened before?" A web tier has no business opening SSH to a database or touching the secrets vault — no signature needed, and TLS doesn't hide who talked to whom. Metadata is the product; that's why losing payload visibility to encryption (including your own!) costs the detection model nothing.

⚠️ Reality check

Kernel-level visibility is not omniscience: a fully kernel-compromised host can lie about its own traffic — which is precisely why the receiving host's agent also reports, and the graph is built from both ends (a liar contradicts its peers). And plan cardinality limits from day one: per-CPU maps with LRU eviction, else a port-scan becomes a memory-exhaustion attack on your own telemetry.

💼 Business lens — the expansion product, and the endgame

This is the classic land-and-expand second act: connectivity lands the agent (tabs 02–05), the flow module is a feature flag away, priced per node per month against NDR budgets that already exist (Corelight, ExtraHop, Darktrace line items). The endgame is act three: the same XDP hook that observes can enforce — first-seen edges can require approval, policies become map entries, and Wormhole grows into a distributed firewall / microsegmentation product. Observe → alert → enforce, all on one deployed binary.

Chapter 07 · Under the hood

07Encryption in XDP: bpf_crypto, key IDs, and zero-loss rotation

Kernel: ≥ 6.10 — bpf_crypto kfuncs Design goal: AEAD (AES-GCM) Rotation: zero packet loss Keys: per-VNI, per-epoch

VXLAN ships with no security whatsoever — anyone on the path can read frames and inject their own. Historically you'd wrap tunnels in IPsec or WireGuard and give back much of the XDP advantage. Since Linux 6.10, the bpf_crypto kfunc family lets an XDP program call into the kernel crypto subsystem directly: userspace creates a cipher context (algorithm + key), pins it where the program can reach it, and the hot path calls bpf_crypto_encrypt() / bpf_crypto_decrypt() without ever leaving the driver. This tab is the full design: wire format, key distribution, and the rotation dance.

The wire format — where every byte goes

⚠️ Reality check — GCM's one commandment, and one kernel caveat

Never reuse a (key, nonce) pair. With AES-GCM a single nonce reuse leaks plaintext XORs and can forge tags. Hence the boring-on-purpose construction: a monotonically increasing 64-bit counter per sender, salt bound to the key epoch, and rekey long before any counter could wrap. Replay is handled WireGuard-style: receivers keep a sliding window per peer and drop stale counters. Second: bpf_crypto coverage of kernel cipher types has been expanding since 6.10 — verify AEAD availability on your target kernel; if your distro's kernel only exposes plain ciphers to BPF, ship the tunnel-mode fallback (kernel WireGuard under the overlay) and keep the wire format ready.

Key rotation with zero packet loss

Rotation fails in the obvious design: flip everyone from K1 to K2 "at the same time" — there is no same time in a distributed system, and every in-flight packet during the flip is garbage to its receiver. The fix is the key_id byte: receivers hold both keys during a transition and let each packet declare which one it used. The Controller runs a three-step epoch state machine:

What the hot path actually looks like

// receive side, inside vxlan_xdp_external — simplified
__u8 key_id = outer_vxh->vx_vni & 0xFF;               // reserved byte → key selector
struct bpf_crypto_ctx **ctx = bpf_map_lookup_elem(&crypto_ctx_map, &key_id);
if (!ctx || !*ctx)
    return XDP_DROP;                                   // unknown epoch → reject, never guess

// nonce = epoch salt ‖ counter from the packet; AAD = VNI ‖ key_id
if (bpf_crypto_decrypt(*ctx, &cipher_slice, &plain_slice, &iv_slice))
    return XDP_DROP;                                   // bad tag = forged/corrupt → drop
// replay window check on counter, then: decap, learn, redirect — your existing code

And it's policy-scoped: same-fabric peers (tab 03) can skip encryption entirely per link, chosen by map flag, not by rebuild.
